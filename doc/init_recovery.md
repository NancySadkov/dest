## Why exact C is blocked

The loader was compiled with TC30 but relies on details that are not
reproduced by straightforward C:

- DGROUP is addressed through overlay segment aliases (`0x0068`, `0x0280`),
  not only through normal near pointers.  The original emits
  `mov ax,0x0068; mov es,ax; mov es:[bx+0xAA0],...`; ordinary C emits
  DS-relative or 32-bit far-pointer arithmetic instead.
- TC converts small constant pushes to `push imm8` (`6A 68`) while the
  original uses `push imm16` (`68 68 00`).
- The original keeps a far pointer in ES:BX across multiple stores; C
  recomputes it unless the exact declaration form is recovered.
- Some calls evaluate the first argument before pushing the second argument;
  the compiler's evaluation order differs for the same call in C.
- `init_assets` is an unrolled asset list, not a loop over a table: 233
  `stshStoreFile` calls and 199 `stshRleType2` calls.

## Functional C tree

`src/init/` now contains the recovered C sources for the three large init
modules:

| File | Original |
|---|---|
| `src/init/assets.c` | `6ffe:02F7` `init_assets` |
| `src/init/assets1.c` | `7a57:0000` `init_assets1` |
| `src/init/assets2.c` | `81b9:0086` `init_assets2` |

They compile and link with:

```text
python scripts/fbov/build_init.py
```

The script compiles the three modules, generates stubs for every external
reference and links a test `init.exe` (95,508 bytes).  The active init
sequence (`main` and `f_3381_0579`) is already C in `src/main.c` and
`src/ov_3381.c`.  The `src/init/` sources are functional, not yet byte-exact,
and are not linked into the standalone build.
